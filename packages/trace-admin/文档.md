# 埋点监控可视化平台 · 前端开发文档 v1.0

## 一、项目概述

本项目旨在设计并实现一个面向前端应用的**埋点监控可视化平台**，用于对页面访问、用户行为、性能指标、错误日志等数据进行统一展示、分析和辅助诊断。平台前端除了承担基础的数据可视化职责外，还将引入 AI 增强能力，对异常指标进行解释、预警和优化建议输出，从而提升平台的智能化分析水平。

平台整体目标包括：

1. 对核心业务数据进行总览展示，帮助使用者快速掌握系统运行状态。
2. 对性能、行为、错误等多维度监控数据进行专项分析。
3. 通过 AI 推荐侧边栏和诊断弹窗，增强异常发现与问题定位能力。
4. 形成统一的数据类型规范、组件规范和开发规范，保证多人协作开发过程中的一致性与可维护性。

## 二、技术栈选型

### 1. 前端框架

- **React 18**
- 基于 **Hooks** 进行函数式组件开发

选择原因：

- 生态成熟，适合中后台和数据可视化类项目
- Hooks 便于逻辑复用和状态拆分
- 与 Ant Design、ECharts、Vite 配合较好

### 2. 开发语言

- **TypeScript**

要求：

- 所有核心数据结构必须定义类型
- 禁止在业务代码中随意使用 `any`
- 组件 props、接口返回值、图表数据均需有明确类型约束

### 3. UI 组件库

- **Ant Design 5.0**

主要用途：

- Layout 布局
- Menu 菜单
- Card、Table、Tabs、Drawer、Modal 等通用 UI
- 保证中后台风格统一

### 4. 图表可视化库

- **ECharts**

主要用途：

- 折线图、柱状图、环形图、仪表盘、瀑布图等数据展示
- 适合复杂图表封装和交互扩展

### 5. 构建工具

- **Vite**

优势：

- 启动快，适合多人协作开发
- 对 React + TypeScript 支持友好
- 本地开发体验较好

## 四、核心功能模块分配

---

### 4.1 骨架搭建与全局配置（队长负责）

#### 功能内容

1. **Layout 基础搭建**
   - 使用 Antd `Layout` 实现整体页面骨架
   - 包含顶部导航、侧边菜单、内容区
   - 预留 AI 侧边栏区域

2. **AI 侧边栏**
   - 实现一个常驻或可折叠的右侧边栏
   - 用于展示 AI 智能推荐卡片
   - 后续所有模块的异常提示都统一从该区域展示

3. **路由配置**
   - 首页总览
   - 性能分析
   - 用户行为分析
   - 错误监控
   - 可预留 AI 分析中心页

4. **全局数据模型定义**
   - 先在 `src/types` 中定义核心类型
   - 作为各模块开发的统一依据，避免数据结构冲突

#### 建议优先完成的类型

- `MetricData`
- `RankingItem`
- `WebVitalMetric`
- `LogDetail`
- `AiSuggestion`

---

### 4.2 平台首页总览（队长负责）

#### 功能内容

1. **核心业务指标卡片**
   - PV
   - UV
   - 今日错误总量
   - 可附带迷你趋势图（sparkline）

2. **稳定性指标**
   - 今日错误总量
   - 环比变化率
   - 升降状态显示

3. **性能仪表盘**
   - 使用仪表盘展示 LCP
   - 按区间显示优 / 中 / 差状态

4. **风险排行**
   - 高频错误 Top5
   - 最慢接口 Top5
   - 使用统一排名表格组件展示

#### 页面目标

首页应作为整个平台的“总控制台”，让使用者在最短时间内了解系统当前状态。

---

### 4.3 性能分析模块（组员 A 负责）

#### 功能内容

1. **Web Vitals 展示**
   - FP
   - FCP
   - LCP
   - CLS
   - TTI

2. **达标率展示**
   - 每个指标使用进度条或状态条表示达标率

3. **资源加载分析**
   - 瀑布图：展示 JS / CSS / 图片等资源的加载时序
   - 分布统计：资源类型耗时占比柱状图

4. **接口监控**
   - 平均响应时间折线图
   - 接口成功率环形图
   - 请求方式 GET / POST 分布图

#### 页面目标

从前端性能角度定位瓶颈，帮助使用者分析影响加载速度和用户体验的关键问题。

---

### 4.4 用户行为分析模块（组员 B 负责）

#### 功能内容

1. **流量分析**
   - 页面访问量排行表格
   - 可展示 PV、UV 等指标

2. **停留时长分析**
   - 页面平均停留时间
   - 使用数字卡片 + 趋势折线图展示

3. **流失分析**
   - 结合埋点中的进入/离开时间戳
   - 可视化展示关键路径中的流失情况
   - 可考虑漏斗图或关键流程路径图

#### 页面目标

帮助分析用户访问习惯、页面吸引力与核心流程中的流失点，为产品优化提供依据。

---

### 4.5 错误监控模块（队长负责）

#### 功能内容

1. **趋势统计**
   - 24 小时错误波动折线图

2. **错误分类**
   - JS 运行错误
   - 资源加载异常
   - Promise 错误
   - 接口错误
   - 使用环形图展示各类错误占比

3. **详情还原**
   - 错误详情列表
   - 折叠面板展示堆栈信息、代码位置、页面路径等

4. **影响评估**
   - 每类错误影响的 PV 数
   - 每类错误影响的用户数

#### 页面目标

支持从错误趋势、错误类型、错误详情和影响范围四个层面分析系统稳定性问题。

## 五、AI 增强功能（全员配合）

AI 能力是本项目的重要亮点，但必须与真实监控数据结合，不能只停留在展示层。

### 5.1 智能诊断

当用户点击错误详情时，弹出 AI 分析弹窗，输出：

- 根因推断
- 可疑触发条件
- 修复建议
- 排查优先级建议

### 5.2 主动扫描

AI 侧边栏根据数据自动生成异常提醒卡片，例如：

- API 成功率下跌 18%
- 高频错误激增
- 某页面停留时长异常下降
- LCP 持续超阈值

### 5.3 性能优化建议

当 LCP、CLS 等性能指标异常时，AI 自动输出更可执行的建议，如：

- 图片压缩建议
- WebP 转换命令
- 懒加载建议
- 资源拆包建议
- 缓存配置建议

## 六、AI 触发规则表

为保证 AI 推荐具有可解释性，AI 推荐内容应基于规则表生成，而不是写死固定文案。

| 触发条件             |    阈值 | 风险等级 | AI 输出建议                                            |
| -------------------- | ------: | -------- | ------------------------------------------------------ |
| API 成功率下降       |    >10% | 高       | 提示查看失败接口排行，建议排查接口异常、超时和重试机制 |
| LCP 超标             | >2500ms | 中       | 建议压缩首屏图片、使用 WebP、优化懒加载策略            |
| CLS 超标             |   >0.25 | 中       | 建议检查图片尺寸占位、避免异步插入 DOM                 |
| 高频错误增长         |    >20% | 高       | 建议定位新增异常类型、查看关联页面与用户影响           |
| 页面停留时长异常下降 |    >15% | 中       | 建议排查页面性能、交互可用性与流程中断问题             |
| 资源加载时间激增     |    >20% | 中       | 建议分析资源体积、CDN 缓存、构建拆包情况               |

## 九、页面状态规范

所有页面和图表必须处理以下四种状态：

1. **loading**
2. **success**
3. **empty**
4. **error**

建议：

- loading：Skeleton / Spin
- empty：展示统一 EmptyState
- error：展示错误提示与重试按钮
- success：正常渲染图表和表格

禁止只实现“有数据时的成功状态”。

## 十、Mock 数据与联调方案

在后端 `server` 模块未完成前，前端统一采用 Mock 数据进行开发。

### 10.1 Mock 原则

- 所有模块数据统一放在 `src/mock`
- 页面不能直接写死示例数据
- 示例值可参考文档中的：
  - PV: 48,293
  - LCP: 2340 ms
  - 今日错误数等

### 10.2 接口适配原则

- 所有页面统一通过 `src/api` 获取数据
- `src/api` 当前读取 mock 数据
- 后端接口完成后，仅替换 `api` 层实现，不直接修改页面逻辑

## 十四、开发规范建议

### 14.1 TypeScript 规范

- 所有接口返回值必须有类型定义
- 所有组件 props 必须有接口定义
- 尽量避免 `any`
- 枚举状态优先使用联合字面量类型

### 14.2 组件规范

- 所有公共组件放在 `src/components`
- 页面级组件不直接承载过多业务逻辑
- 图表配置项尽量抽离为独立函数

### 14.3 命名规范

- 组件文件使用 PascalCase
- hooks 统一以 `use` 开头
- 工具函数使用 camelCase
- 类型文件命名尽量语义化

### 14.4 数据流规范

- 页面不直接访问 mock
- 所有数据统一通过 `api` 获取
- 所有 server 返回的数据必须有类型约束

## 十七、总结

本开发文档的目标不是只罗列功能，而是保证项目具备以下三点：

1. **结构清晰**：目录、模块、组件、类型统一
2. **协作顺畅**：数据结构一致，模块边界清晰
3. **演示完整**：不仅有监控看板，还有 AI 异常分析亮点

整个项目建议优先完成基础架构、公共层和首页总览，再推进专项模块，最后统一接入 AI 增强逻辑。这样既能保证开发效率，也能减少多人协作中的返工成本。
